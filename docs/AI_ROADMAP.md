# me-budget — แผนใช้ AI เพิ่ม (draft)

ตอนนี้ AI มีจุดเดียวคือสแกนใบเสร็จ (FR-10, `src/infrastructure/ai/GeminiReceiptParser.ts`) ใช้ Gemini + zod schema เป็นสัญญา เอกสารนี้จดแผนต่อยอดไว้ก่อน **ยังไม่เริ่มทำ**

## ข้อจำกัด (ต้องคิดทุกฟีเจอร์)
- **Gemini free tier** ยอมให้ Google เอาข้อมูลไปใช้ (TECH_DESIGN T5) → ส่งข้อมูลออกให้น้อยที่สุด ส่งยอดรวมได้ก็อย่าส่งรายการดิบ
- **โควตา AI ต่อบัญชี บังคับแล้ว (เฟส 0)** ค่าเริ่มต้น 20 ครั้ง/วัน ใช้ร่วมกันทุกฟีเจอร์ (`AI_DAILY_LIMIT`) · ผู้ใช้เห็นจำนวนที่เหลือ (`GET /api/ai-budget`) → ฟีเจอร์ใหม่ต้องนับใต้ key `ai:<userId>` เดียวกัน
- **หัวใจคือจดเร็ว** (FR-1) → ฟีเจอร์ AI ห้ามทำให้ flow หลักช้าลง และต้องมีทางจดมือเสมอเมื่อ AI ล้ม
- **ไม่ผูกบัญชีธนาคาร** (TOR หัวข้อ 3) → นำเข้าจากรูป/ไฟล์ที่เราส่งเองได้ แต่ไม่ต่อ API ธนาคาร

| 3 ✅ | **สรุปรายเดือนเป็นภาษาคน** 3 บรรทัด | ส่งแค่ยอดรวมต่อหมวด ไม่ส่งรายการดิบ · สร้างเดือนละครั้งแล้ว cache · ทำคู่กับ FR-6 · ดูหัวข้อ "เฟส 3" ด้านล่าง |

โครงเดียวกันทุกฟีเจอร์: port ใน `application/ports` → adapter ใน `infrastructure/ai` → zod schema เป็นสัญญา → AI ล้มก็กลับไปจดมือ

## เฟส 1: สแกนอะไรก็ได้ (Smart scan)

**สถานะ: เขียนโค้ดแล้ว ยังไม่ได้ลองกับรูปจริงและ Gemini จริง** (เทสต์ใช้ mock) · สิ่งที่ทำจริง:
- AI ตอบ `kind` + ข้อมูลในครั้งเดียว (ใช้ schema เดียวกับใบเสร็จ เพิ่ม `kind` และ `fees`) · `unknown` ถูกตีเป็น `INVALID_RECEIPT`
- **ค่าส่ง/ค่าบริการ/ทิป = บรรทัดใบเสร็จ** ที่เจ้าของคือ "เรา + ทุกคนในบิล" ระบบหารเท่าเดิม (ปัดเศษลงต่อคน เศษเป็นของเรา) ไม่ต้องแก้ DB · ได้หมวดเดียวกับสินค้าที่แพงสุด · ความจำเจ้าของไม่ถูกใช้กับบรรทัดค่าส่ง
- **ส่วนลดเกลี่ยตามสัดส่วนราคาทุกบรรทัด รวมบรรทัดค่าส่งด้วย** ดังนั้นถ้าส่วนลดเป็นของค่าส่งโดยเฉพาะ (ส่งฟรี) ค่าส่งที่หารอาจเพี้ยนเล็กน้อย → หน้าตรวจขึ้นเตือน "ผลรวมไม่ตรง" ให้แก้ได้
- **สลิปโอน:** ทำเป็นใบเสร็จ 1 บรรทัดผ่านหน้าตรวจเดิม (ไม่ได้ไปหน้าจดปกติที่กรอกไว้ให้ตามที่วางแผนไว้แรก — ต้องเดินสาย prefill เพิ่ม ไว้ทำทีหลังถ้าจำเป็น)
- **`history` ยังไม่แยกประเภท** AI จะตอบ `unknown` → ขึ้นข้อความอ่านไม่ได้ (เฟส 1.5)
- ย่อรูปก่อนอัปโหลดใหม่ (`uploadScale`): แคปหน้าจอยาวคงความกว้างอย่างน้อย ~900px สูงไม่เกิน 4096px

แนวคิด: ไม่ใช่แค่ใบเสร็จ แคปรูปอะไรมาก็ได้ ระบบต้องรู้เองว่าเป็นอะไรและแยกให้

| รูปแบบ (`kind`) | ตัวอย่าง | ได้อะไรออกมา | ไปหน้าไหน |
|---|---|---|---|
| `receipt` | บิล 7-11 / ซูเปอร์ฯ | รายการสินค้า (มีอยู่แล้ว) | หน้าตรวจรายการ (ItemizedScreen) |
| `delivery` | ออเดอร์ Grab / LINE MAN / foodpanda | รายการอาหาร + **ค่าส่ง/ค่าบริการ** + ส่วนลด | หน้าตรวจรายการ + หารกับคนได้ |
| `online_order` | ออเดอร์ Shopee / Lazada | รายการสินค้า + ค่าส่ง + ส่วนลด | หน้าตรวจรายการ |
| `transfer_slip` | สลิป PromptPay / แอปธนาคาร | 1 รายการ: ยอด เวลา ชื่อผู้รับ เดาหมวด | หน้าจดปกติ กรอกไว้ให้แล้ว |
| `history` | หน้าประวัติรายการในแอปธนาคาร/e-wallet | หลายรายการ → เฟส 1.5 | หน้าจดย้อนหลัง |
| `unknown` | รูปที่ไม่เกี่ยวกับเงิน | — | แจ้ง "รูปนี้อ่านเป็นรายจ่ายไม่ได้" แล้วให้จดมือ |

**วิธีทำ (แนะนำ):**
- **เรียก AI ครั้งเดียว** ให้ตอบ `kind` + ข้อมูลในก้อนเดียว ไม่แยกเป็น "จำแนกก่อนแล้วค่อยอ่าน" เพราะจะเสีย 2 เท่าทั้งโควตาและเวลา
- ขยาย schema เดิมใน `GeminiReceiptParser.ts`: เพิ่ม `kind`, `fees[]` (ค่าส่ง ค่าบริการ), `counterparty` (ชื่อผู้รับในสลิป), `time`, `transactions[]` (สำหรับ `history`)
- ต้องลองกับรูปจริงก่อนว่า `flash-lite` ตอบ schema ที่ใหญ่ขึ้นได้แม่นพอไหม (`scripts/try-receipt.ts`) ถ้าไม่พอค่อยแยกเป็นสองครั้ง
- ความจำเจ้าของ + การเดาเจ้าของรายบรรทัดใช้กับ `delivery` / `online_order` ได้เหมือนใบเสร็จ

**ต้องตัดสินใจ:**
- **ค่าส่ง/ค่าบริการหารยังไง** ตอนนี้ `allocateToBillTotal` จะเกลี่ยส่วนต่างตามสัดส่วนราคา (ใครสั่งแพงจ่ายค่าส่งมาก) → แนะนำ: **ค่าส่ง/ค่าบริการหารเท่ากันทุกคนในบิล ส่วนลดเกลี่ยตามสัดส่วน**
- **หน้าเลือก "หารกับใคร?"** ตอนนี้ถามก่อนถ่ายรูป ถ้าเป็นสลิปโอนไม่ต้องถาม → ยังถามก่อนได้ (ไม่เลือกใครก็ได้) ไม่ต้องเปลี่ยน flow

**ความเสี่ยง:**
- **แคปยาว (long screenshot) จะอ่านไม่ออก:** `resizeForUpload` บีบด้านยาวสุดเหลือ 1600px (`src/client/resizeImage.ts:2`) รูป 1080×6000 จะเหลือกว้างราว 290px → ต้องจำกัดที่ความกว้างแทน หรือตัดรูปเป็นท่อน
- **สลิป/ประวัติมีชื่อ เลขบัญชี ยอดคงเหลือ** ถูกส่งไป Gemini free tier ด้วย (T5) — ไม่เก็บรูปเหมือนเดิม และสั่ง AI ไม่ต้องดึงเลขบัญชี/ยอดคงเหลือออกมา

## เฟส 1.5: จดย้อนหลังทีเดียวหลายรายการ

**สถานะ: เขียนโค้ดแล้ว ยังไม่ได้ลองกับรูปจริงและ Gemini จริง** (เทสต์ใช้ mock, build ผ่าน) · สิ่งที่ทำจริง:
- `kind: history` ใหม่ใน schema เดิม → `transactions[]` (วันที่ รายละเอียด จำนวน เข้า/ออก หมวด) จำกัด 60 แถว · ไม่ให้ AI ดึงยอดคงเหลือ/เลขบัญชี
- ปุ่ม "เลือกจากอัลบั้ม" เลือกได้หลายรูป (สูงสุด 10) อ่านทีละรูป (1 รูป = 1 โควตา) · 1 รูปที่เป็นใบเสร็จ/ออเดอร์ยังเข้าหน้าตรวจรายการเดิม · หลายรูป หรือรูปประวัติ → หน้า "จดย้อนหลัง" (`BackfillReview`) · ใบเสร็จที่อยู่ในชุดหลายรูปถูกย่อเป็น 1 แถวยอดรวม (ไม่แยกรายการสินค้า)
- **กันซ้ำ** (`POST /api/backfill/check` ไม่ใช้ AI/โควตา): วัน+ชนิด+จำนวนตรงกับรายการที่จดไว้ หรือแถวเดียวกันเป๊ะซ้ำในชุดเดียวกัน (แคปทับกัน) → ป้าย "อาจซ้ำ" และไม่ติ๊กให้
- **บันทึก** (`POST /api/backfill`) ทีเดียว all-or-nothing ในทรานแซกชันเดียว นับเป็นการจด **1 ครั้งของวันนี้** (XP/streak ครั้งเดียว) ไม่เติม streak ให้วันเก่า · รายการเป็น `source = manual` ใส่รายละเอียดไว้ในโน้ต · เข้ากระเป๋าเดียวทั้งชุด
- ตัวเลือกแก้ในหน้าตรวจ: ติ๊ก, รายละเอียด, รายรับ/รายจ่าย, จำนวน, หมวด · **การโอนระหว่างกระเป๋าตัวเองยังต้องจดเป็น "โอน" เอง** (AI ไม่รู้ว่าบัญชีไหนเป็นของเรา) ตอนนี้จะเข้าเป็นรายจ่าย/รายรับธรรมดา ให้ติ๊กออก
- วันที่ที่อ่านไม่ออกหรืออยู่ในอนาคต → วันนี้
- ยกเลิกหลังบันทึก (ย้อนกลับ 5 วินาที) ลบทั้งชุด

- **2 ทางเข้า:** (ก) แคปหน้าประวัติ 1 รูป มีหลายรายการ (ข) เลือกหลายรูปจากอัลบั้มพร้อมกัน (เช่น สลิป 5 ใบ) แต่ละรูปผ่านเฟส 1
- **หน้าตรวจ:** ลิสต์ร่างทั้งหมด แต่ละแถวมี ✓ ยอด เวลา หมวดที่เดา แตะเพื่อแก้ได้ · กดบันทึกทีเดียว
- **กันซ้ำ:** แถวที่ยอดเท่ากับรายการที่จดไว้แล้วในวันเดียวกัน → ติดป้าย "อาจซ้ำ" และ**ไม่ติ๊กไว้ให้**
- **เงินเข้า vs เงินออก:** หน้าประวัติมีทั้งสองอย่าง → ร่างเป็นรายรับ/รายจ่ายตามเครื่องหมาย · รายการที่เป็นการโอนระหว่างกระเป๋าตัวเอง ให้ผู้ใช้เปลี่ยนเป็น "โอน" เอง (AI ไม่รู้ว่าบัญชีไหนเป็นของเรา)
- **Streak:** จดย้อนหลัง**ไม่ช่วยต่อ streak** ของวันที่ลืมจด เพราะ streak นับจากเวลาที่กดจด (TOR FR-7 ตัดสินใจไว้แล้ว, `src/application/log-activity.ts`) · บันทึกทีเดียวหลายรายการนับเป็นการจด 1 ครั้งของวันนี้
- **โควตา:** 1 รูปประวัติ = 1 ครั้ง · เลือก 5 รูป = 5 ครั้ง → ต้องมีเฟส 0 ก่อน

## เฟส 3: สรุปรายเดือนเป็นภาษาคน ✅

widget "สรุปเดือนนี้ (AI)" บน dashboard · `GET /api/summary?month=YYYY-MM` · use case `GetMonthSummary` · adapter `GeminiMonthSummarizer.ts` · ตาราง `monthly_summaries` (migration 008)

- **ส่งอะไรให้ Gemini:** เฉพาะตัวเลขรวม — ยอดจ่ายของเรา (ไม่รวมส่วนของคนอื่น) ต่อหมวดของเดือนนี้และเดือนก่อน, ชื่อหมวด, จำนวนวันที่จด / วัน no-spend · **ไม่ส่ง**รายการดิบ โน้ต ร้านค้า ชื่อคน หรือบรรทัดใบเสร็จ (test ตรวจว่า payload มีแค่นี้)
- **คำนวณในโค้ด ไม่ใช่ในโมเดล:** % เปลี่ยนแปลงรวมและรายหมวดคิดใน `GetMonthSummary` แล้วส่งเป็นข้อเท็จจริง โมเดลมีหน้าที่แค่เรียบเรียงเป็นภาษาคน (prompt สั่งให้ใช้เฉพาะตัวเลขที่ให้ ห้ามคิดหรือแต่งตัวเลขเอง) ยอดเงินแปลงสตางค์เป็นบาทตอนสร้าง prompt
- **เดือนที่ยังไม่จบ:** เทียบ "วันที่ 1 ถึงวันนี้" กับ "วันที่ 1 ถึงวันเดียวกันของเดือนก่อน" ไม่เอายอดครึ่งเดือนไปเทียบกับทั้งเดือน
- **กฎ cache (ตัดสินใจแล้ว):** เดือนที่จบแล้ว สร้างครั้งเดียวแล้วไม่สร้างใหม่อีก · เดือนปัจจุบัน สร้างใหม่ได้**ไม่เกินวันละครั้ง** (ตามวันเวลาไทย) ไม่มีปุ่ม refresh แยก · เดือนที่ยังไม่มีรายจ่าย (รวมเดือนในอนาคต) ตอบข้อความตายตัว "เดือนนี้ยังไม่มีรายจ่ายให้สรุป" โดยไม่เรียก AI ไม่นับโควตา ไม่เก็บ
- **โควตา:** เรียก AI จริงนับ 1 ครั้งใต้ key `ai:<userId>` ร่วมกับฟีเจอร์อื่น (helper `src/application/ai-budget.ts`) · cache hit ไม่นับ · เรียกล้มก็นับ · เกิน → `RATE_LIMITED`
- **UI:** widget เปิดไว้เป็นค่าเริ่มต้นแต่**ไม่เรียก AI ตอนเปิดหน้า** ต้องกด "สรุปให้หน่อย" ก่อน (ปิดได้ที่ "แก้ dashboard") · ล้มเหลวขึ้นข้อความสุภาพ ไม่กระทบส่วนอื่น (ไม่ retry เองเพราะแต่ละครั้งกินโควตา)
- **ยังไม่ได้ลองกับ Gemini จริง:** คุณภาพประโยคและความเชื่อฟัง "ใช้เฉพาะตัวเลขที่ให้" ต้องลองกับข้อมูลจริงก่อนปล่อย (ตัดผลลัพธ์ที่ 400 ตัวอักษรเป็นเพดานกันยาวเกิน)
